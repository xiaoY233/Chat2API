# Windows native proxy services

Chat2API and LiteLLM can run as native Windows processes when Docker or WSL
must be stopped during local development. This keeps existing API connections
independent from the Docker Desktop lifecycle.

The native supervisor only manages processes and health checks. It does not
retry, replay, or alter API requests.

## Scripts

- `scripts/windows/install-chat2api-native-runtime.ps1` installs a built
  Chat2API server bundle and production Node dependencies into a new runtime
  directory.
- `scripts/windows/new-chat2api-native-config.ps1` imports the existing
  container environments, applies native host paths and ports, and writes a
  DPAPI-encrypted supervisor configuration.
- `scripts/windows/chat2api-native-supervisor.ps1` starts and health-checks
  Chat2API and LiteLLM in dependency order.
- `scripts/windows/register-chat2api-native-supervisor.ps1` registers the
  supervisor as a current-user scheduled task.

Docker is required only while importing the existing container environment and
copying the persistent Chat2API data. It is not required after the native
services are active.

## Prerequisites

- A production Chat2API server build from `npm run build:server`.
- A Windows Python virtual environment containing the required LiteLLM version
  and the repository's Anthropic stream patch.
- A native LiteLLM dependency set validated with `python -m pip check` and a
  startup smoke test. Optional database exception handling must include the
  `prisma` package used by the source container.
- Existing Chat2API and LiteLLM containers from which environment values can be
  imported.

Do not copy a Linux native extension into the Windows virtual environment.
LiteLLM's Rust bridge is optional and falls back to its Python implementation.

## Install Chat2API

Build the server first, then install it into a new versioned directory:

```powershell
$nativeRoot = Join-Path $env:LOCALAPPDATA 'Chat2API\native'
.\scripts\windows\install-chat2api-native-runtime.ps1 `
  -SourcePath 'C:\path\to\built\Chat2API' `
  -DestinationPath (Join-Path $nativeRoot 'chat2api-<revision>')
```

The installer deliberately refuses to overwrite an existing destination.
This keeps the previous runtime available for rollback.

## Create the supervisor config

Create the destination data directory before generating the config. During an
actual cutover, stop the Chat2API container before copying its final data so
the copy is consistent.

```powershell
$nativeRoot = Join-Path $env:LOCALAPPDATA 'Chat2API\native'
.\scripts\windows\new-chat2api-native-config.ps1 `
  -Chat2ApiSourcePath (Join-Path $nativeRoot 'chat2api-<revision>') `
  -Chat2ApiDataPath (Join-Path $nativeRoot 'data-<revision>') `
  -LiteLlmVenvPath (Join-Path $nativeRoot 'litellm-venv') `
  -LiteLlmConfigPath (Join-Path $nativeRoot 'litellm\config.yaml') `
  -Chat2ApiContainer 'chat2api' `
  -LiteLlmContainer 'chat2api-litellm' `
  -Chat2ApiPort 18080 `
  -LiteLlmPort 4000 `
  -ConfigPath (Join-Path $nativeRoot 'supervisor-config.clixml') `
  -LogDirectory (Join-Path $nativeRoot 'logs')
```

Every imported environment value is stored as a `SecureString` protected by
Windows DPAPI. The config ACL is restricted to the current Windows user. A
config generated by one user cannot be used by a task running as another user.
The generated schema records a named `chat2api` dependency and the exact
Chat2API health URL used by LiteLLM. The supervisor will not start or keep the
LiteLLM process active while that dependency is unavailable.

The Docker Compose deployment uses Chat2API port `8080`; the native example
uses `18080` to avoid binding two instances to the same listener. Choose one
topology for the active proxy chain and regenerate the config whenever the
Chat2API host or port changes. Existing schema-1 configs remain readable, but
should be regenerated so their dependency metadata is explicit.

## Validate before cutover

Use unused loopback ports first. Run a single supervisor check and verify both
health endpoints:

```powershell
.\scripts\windows\chat2api-native-supervisor.ps1 `
  -ConfigPath $configPath `
  -MutexName 'Local\Chat2API.NativeSupervisor.Stage' `
  -Once
```

Validation should cover:

- Chat2API and LiteLLM health/readiness endpoints.
- Authenticated model listing and unauthenticated rejection.
- Anthropic `count_tokens`.
- Non-streaming and streaming messages.
- Client cancellation returning Chat2API's active connection count to zero.

## Cutover order

1. Confirm Chat2API reports zero active connections and no client is connected
   to the LiteLLM port.
2. Stop and disable the Docker watchdog so it cannot reclaim the production
   ports.
3. Stop LiteLLM, then Chat2API, without deleting either container.
4. Copy the frozen Chat2API data volume into the native data directory.
5. Run the native supervisor once and complete the production-port smoke test.
6. Register and start the persistent supervisor task:

```powershell
.\scripts\windows\register-chat2api-native-supervisor.ps1 `
  -ConfigPath $configPath `
  -SupervisorPath $supervisorPath `
  -TaskName 'Chat2API Native Supervisor' `
  -Start
```

The scheduled task runs as the current interactive user because that identity
is required to decrypt the DPAPI environment values.

## Rollback

Stop the native supervisor task, stop only the PIDs recorded in the configured
PID files after verifying their executable paths, then start the preserved
Chat2API and LiteLLM containers. Re-enable the Docker watchdog only after both
container health checks pass.

Never run native and Docker instances on the same ports. Never replay a failed
request during service recovery because an upstream provider may already have
accepted it.
